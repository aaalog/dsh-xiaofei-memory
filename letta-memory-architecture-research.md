# Letta (原 MemGPT) 记忆实现拆解报告

> 调研时间：2026-11-13。所有结论均标注来源；查不到的一律写「未查到」。
> 重要前提：**Letta 在 2026 年发生过一次架构断代**。`letta-ai/letta`（Python/服务器）已经不再是主线，README 明确指向 `letta-ai/letta-code`（TypeScript harness）。因此论文（2023）、Python 版 memory blocks（2024-2025）、MemFS/Context Repositories（2026-02）是**三代不同的东西**，混着说就会出错。本报告按代拆开讲。

## §1 三层记忆的确切定义（MemGPT 原始架构）

**论文**：Packer et al., *MemGPT: Towards LLMs as Operating Systems*, arXiv:2310.08560v2（2024-02-12 修订）
来源：https://arxiv.org/abs/2310.08560 ｜ 全文 HTML：https://arxiv.org/html/2310.08560v2

### 1.1 总的二分法（不是三分法）

论文的原话是**两层**，不是三层：

> "MemGPT's OS-inspired multi-level memory architecture delineates between two primary memory types: **main context** (analogous to main memory/physical memory/RAM) and **external context** (analogous to disk memory/disk storage). Main context consists of the LLM prompt tokens — anything in main context is considered in-context and can be accessed by the LLM processor during inference. External context refers to any information that is held outside of the LLMs fixed context window."
> —— §2 开头，https://arxiv.org/html/2310.08560v2

所谓「core / archival / recall 三层」，是**main context 内部的 working context + external context 的两个数据库**这种叫法，是工程实现（后来的 Letta）固化的术语，论文本身用的是 main context / external context。

### 1.2 Main context 的三个连续区块（关键：这就是「分页」的落点）

> "The prompt tokens in MemGPT are split into three contiguous sections: the **system instructions**, **working context**, and **FIFO Queue**. The system instructions are read-only (static) and contain information on the MemGPT control flow, the intended usage of the different memory levels, and instructions on how to use the MemGPT functions... Working context is a fixed-size read/write block of unstructured text, **writeable only via MemGPT function calls**... The FIFO queue stores a rolling history of messages, including messages between the agent and user, as well as system messages (e.g. memory warnings) and function call inputs and outputs. The first index in the FIFO queue stores a system message containing a **recursive summary** of messages that have been evicted from..."
> —— §2.1，https://arxiv.org/html/2310.08560v2

| 层 | 物理位置 | 谁负责搬动 | 是否常驻上下文 |
|---|---|---|---|
| **system instructions** | prompt 前缀，只读 | 无人（静态） | 是 |
| **working context**（≈ 后来的 core memory） | prompt 中部，固定大小可读写文本块 | **只能通过 LLM 自己调函数改** | 是，永远可见 |
| **FIFO queue**（≈ recall 的入口） | prompt 尾部，滚动消息历史 | **queue manager 自动驱逐**，LLM 可主动检索 | 是，但会滚动 |
| **recall storage**（消息库） | 外部数据库 | queue manager 写入；LLM 用 `conversation_search` 取回 | 否 |
| **archival storage** | 外部数据库（任意长文本） | LLM 用 `archival_memory_insert/search` 自行读写 | 否 |

### 1.3 「分页」机制的确切含义

论文明确用 OS 的 page fault 做类比：

> "Applications in traditional OSes interact with virtual memory, which provides an illusion of there being more memory resources than are actually available in physical (i.e., main) memory by the OS paging overflow data to disk and retrieving data (via a page fault) back into memory when accessed by applications."
> —— §1，https://arxiv.org/html/2310.08560v2

> "These capabilities allow LLMs to effective 'page' in and out information between context windows (analogous to 'main memory' in operating systems) and external storage, similar to hierarchical memory in traditional OSes."
> —— §1，同上

**分页的两个层次**（这点很容易漏）：

1. **被动分页（runtime 做）**：FIFO queue 溢出 → queue manager 驱逐 + 生成递归摘要。这是**运行时自动**的，不需要 LLM 同意（但有预警）。
2. **主动分页（LLM 做）**：archival/recall 检索时，**检索结果本身也要分页**，防止一次检索就把上下文撑爆：

> "our memory retrieval mechanisms are designed to be cognizant of these token constraints and implement **pagination** to prevent retrieval calls from overflowing the context window."
> —— §2.3，https://arxiv.org/html/2310.08560v2

### 1.4 为什么必须让 agent 自己调工具（self-editing memory）

论文的因果关系非常直接：

> "MemGPT orchestrates data movement between main context and external context via function calls that are generated by the LLM processor. Memory edits and retrieval are entirely **self-directed**: MemGPT autonomously updates and searches through its own memory based on the current context."
> —— §2.3

> "We implement self-directed editing and retrieval by providing explicit instructions within the system instructions that guide the LLM on how to interact with the MemGPT memory systems. These instructions comprise two main components: (1) a detailed description of the memory hierarchy and their respective utilities, and (2) a **function schema (complete with their natural language descriptions)** that the system can call to access or modify its memory."
> —— §2.3

**照抄要点**：MemGPT 的「智能」不在检索算法里，而在**把 schema + 何时用的判断交给模型**。runtime 只提供：schema、执行器、溢出兜底。

### 1.5 论文里的 system prompt 结构

论文附录 §6.1 只给了 DMR（deep memory retrieval）任务的精简版，并明确说：

> "The MemGPT prompts have been edited for brevity. For full implementation details (including exact prompts) visit https://research.memgpt.ai."
> —— §6.1.1，https://arxiv.org/html/2310.08560v2

**完整版 prompt 来自官方仓库**（`letta-ai/letta` 的 `archive` 分支，文件 `letta/prompts/system_prompts/memgpt_chat.py`）：
https://raw.githubusercontent.com/letta-ai/letta/archive/letta/prompts/system_prompts/memgpt_chat.py

它的骨架（原文小标题）依次是：

1. `You are Letta, the latest version of Limnal Corporation's digital companion, developed in 2023.`（人格设定）
2. **Realism and authenticity** — 永不说自己是 AI
3. **Control flow** — 核心：「Unlike a human, your brain is not continuously thinking, but is run in short bursts.」解释 heartbeat / 连续推理
4. **Core memory (limited size)** — 原文：
   > "Your core memory unit is held inside the initial system instructions file, and is always available in-context (you will see it at all times)... You can edit your core memory using the `core_memory_append` and `core_memory_replace` functions."
5. **Archival memory (infinite size)** — 原文：
   > "Your archival memory is infinite size, but is held outside your immediate context, so you must explicitly run a retrieval/search operation to see data inside it."
6. **Recall memory** — 原文：
   > "You can search your recall memory using the `conversation_search` function."
7. `send_message` — 「`send_message` is the ONLY action that sends a notification to the user. The user does not see anything else you do.」

### 1.6 论文/原版的 function 列表（确认到的）

| 函数 | 作用 | 来源 |
|---|---|---|
| `send_message` | 唯一对用户可见的输出通道 | prompt 原文 L28-29 |
| `conversation_search` | 检索 recall storage（历史消息） | prompt 原文 L42 |
| `core_memory_append` | 向 core block 追加 | prompt 原文 L50 |
| `core_memory_replace` | 替换 core block 中精确子串（删就用空串） | prompt 原文 L50 + `base.py` 实现 |
| `archival_memory_insert` | 写入 archival | prompt 原文 L55 |
| `archival_memory_search` | 语义检索 archival | prompt 原文 L55 |

**function chaining / heartbeat**：
> "The LLM can request immediate follow-up LLM inference to chain function calls together by generating a special keyword argument (**`request_heartbeat=true`**) in its output; function chaining is what allows MemGPT to perform multi-step retrieval to answer user queries."
> —— §2.4，https://arxiv.org/html/2310.08560v2

这是「单次记忆操作要几轮 LLM 调用」的根源（见 §5.6）。

## §2 Memory blocks 机制细节（Python 版，2024-2025）

### 2.1 定义

官方现行文档把它标为 `status: legacy`，但定义写得最清楚：

> "Memory blocks are structured sections of the agent's context window that persist across all interactions. They are always visible - no retrieval needed. **Under the hood, memory blocks are simply prepended to the agent's prompt in an XML-like format.**"
> —— https://docs.letta.com/v1-sdk/memory/memory-blocks

三元组（实际是四元组）：

> "A memory block consists of: A `label`, which is a unique identifier for the block; A `description`, which describes the purpose of the block; A `value`, which is the contents/data of the block; A `limit`, which is the size limit (in characters) of the block."
> —— 同上

注入到 prompt 的真实形态（官方文档给出的原文）：

```xml
<memory_blocks>
<persona>
<description>The persona block: Stores details about your current persona...</description>
<metadata>
- chars_current=128
- chars_limit=5000
</metadata>
<value>I am a helpful assistant named Sam. ...</value>
</persona>
```

注意 `chars_current` / `chars_limit` 是**显式写进 prompt 给模型看的**——这是「让模型自己管预算」的设计，不是给程序看的。

### 2.2 容量限制机制与超限行为（重要，且文档没写清）

- **默认 limit = 100,000 字符**（`CORE_MEMORY_BLOCK_CHAR_LIMIT: int = 100000`），另有 `CORE_MEMORY_PERSONA_CHAR_LIMIT = 20000`、`CORE_MEMORY_HUMAN_CHAR_LIMIT = 20000`。
  来源：`letta/constants.py`，https://raw.githubusercontent.com/letta-ai/letta/archive/letta/constants.py
- 文档示例里普遍用 `limit: 5000`。

**超限怎么办**：文档**没有**明确规定。从源码和 issue 看，行为是**「拒绝写入并报错，但旧值可能已被污染」**，实现并不干净：

- `BlockManager.bulk_update_block_values_async` 的 docstring 明确：`Raises: ValueError if any new value exceeds its block's limit`。
  来源：https://raw.githubusercontent.com/letta-ai/letta/archive/letta/services/block_manager.py
- 但实际那段循环里**没有看到显式的长度检查**（只 `block.value = new_val`），说明校验在别处或已被弱化——因此历史上有真实 bug。
- PR #1616 的复现步骤直接描述了故障链：
  > "Make agent core memory (human or persona be 1999 characters with a 2000 limit) Ask agent to save something more to the memory. If it does actually do it, the validation and function call would fail **but the data was still applied to the agent**. On next agent load it will throw an error because the memory is over the limit."
  来源：https://github.com/letta-ai/letta/pull/1616

**结论（可抄的正确做法）**：Letta 这里是「软限制 + 事后报错」，模型看到的只有 `chars_limit` 这个数字，靠模型自觉。**没有自动截断、没有自动摘要进 block、没有硬拒绝的一致性保证**。这是它的坑之一，抄的时候应该做成 pre-write 硬校验。

### 2.3 `core_memory_append` / `core_memory_replace` 现在还在不在？

**分三阶段回答（这是最容易搞错的地方）**：

| 阶段 | 工具名 | 证据 |
|---|---|---|
| 2023 论文 / 初版 | `core_memory_append`, `core_memory_replace` | prompt 原文 + `base.py` |
| 2024-2025 Python 版 | 两套并存：老的两个 + 新的 `memory_insert` / `memory_replace` / `memory_rethink` / `memory_apply_patch` / `memory_finish_edits`，以及 omni-tool `memory(command=...)` | `archive` 分支 `letta/functions/function_sets/base.py` |
| 2026 TS 版 | **老名字基本消失**，改为 MemFS 文件工具 + 一个 `Memory` 工具 | `letta-code` 源码 + 2026 文档 |

2025-09 的 omni-tool 公告明确说这是「合并成一个工具」的方向：

> "Agents in Letta can now not only modify existing memory blocks, but also create and delete memory blocks on-the-fly as they learn over time. Previously, enabling an agent to create and delete memory blocks required developers to write custom tools or scripts building on the Letta API - but now, using the new built-in **memory omni-tool**, agents can easily handle it themselves."
> —— https://www.letta.com/blog/introducing-sonnet-4-5-and-the-memory-omni-tool-in-letta/

omni-tool 的 `command` 取值（源码原文）：`create` / `str_replace` / `insert` / `delete` / `rename`。
来源：https://raw.githubusercontent.com/letta-ai/letta/archive/letta/functions/function_sets/base.py

而 2026 的 changelog 里有：
> "Removed legacy **sleeptime-agent, memory-block**, skills-block migration, and block-label plumbing paths"
> —— https://docs.letta.com/reference/changelog

即：**memory block 作为一等抽象在 Letta Code 里已被 MemFS 取代**，老工具名在 2026 文档里查不到（`llms.txt` 全文 grep `core_memory_append` 命中 0）。

### 2.4 block 的渲染是「自动进 system prompt」而非工具注入

`Memory.compile()` 会把所有 block 渲染进 `<memory_blocks>`；而且有分流逻辑：

> "For git-memory-enabled agents, only `system/` blocks are rendered. For standard agents, all blocks are rendered."
> —— `letta/schemas/memory.py`，https://raw.githubusercontent.com/letta-ai/letta/archive/letta/schemas/memory.py

这条是 MemFS 迁移的桥梁：**只有 `system/` 下的 block 还常驻上下文，其余退化为按需读取的文件**。

## §3 MemFS / sleep-time / dreaming

### 3.1 MemFS 是真的，而且是 2026 主线

**官方文档**：https://docs.letta.com/concepts/memfs
**官方博客（2026-02-12）**：https://www.letta.com/blog/context-repositories

> "**MemFS** is how a Letta agent works with its long-term memory. The memory itself is part of the agent's state, held in a **git repository that belongs to the agent**... MemFS **projects** that repository onto whatever computer the agent is running on, as a real checkout the agent reads and edits with ordinary file tools. Edits are local until committed and pushed, at which point they become the agent's memory everywhere. **All Letta agents use MemFS.**"
> —— https://docs.letta.com/concepts/memfs

博客侧的定性：

> "We're introducing **Context Repositories**, a rebuild of how memory works in Letta Code based on **programmatic context management and git-based versioning**... Context Repositories are git-backed, so every change to memory is automatically versioned with informative commit messages. Git tracking also enables concurrent, collaborative work across multiple subagents, which can manage divergence and conflicts between learned context through standard git operations."
> —— https://www.letta.com/blog/context-repositories

**所以是的：把记忆存成 git 版本化的文件树，这个说法准确。**

### 3.2 目录结构（官方文档原文）

```
$MEMORY_DIR/
├── MEMORY.md
├── persona.md
├── human.md
├── reference/
│   ├── MEMORY.md
│   └── project-notes.md
└── skills/
    └── my-skill/
        └── SKILL.md
```

文件格式是 **Markdown + YAML frontmatter**：

```markdown
---
name: persona
description: "Who I am, what I value, and how I approach working with people."
---

I am a Letta agent. I remember durable preferences and improve with use.
```

### 3.3 核心机制：层级即上下文预算（progressive disclosure）

这是整个设计里最值得抄的一条：

> "**Files at the memory root are loaded into the agent's system prompt on every turn.** Use them for the agent's identity, important user preferences, durable project facts, and critical workflow rules... **Directories with their own `MEMORY.md` index stay out of context until they are needed.** The root `MEMORY.md` lists them, so directory and file names act as signposts the agent follows to read the right file. This keeps the active context lean while preserving deeper reference material."
> —— https://docs.letta.com/concepts/memfs

**翻译成工程语言**：`label` 不再只是名字，**label/路径就是「这段记忆是否常驻上下文」的开关**。放在 root = 常驻；放进带 `MEMORY.md` 的子目录 = 惰性加载。

> "Memory is addressed by path: the memory labelled `persona` is projected to `persona.md`. **Choosing a label is choosing where the memory lives and whether it stays in context.**"
> —— 同上

### 3.4 agent 怎么读怎么写

- **写**：用普通文件工具（Write/Edit/ApplyPatch）直接改 checkout，然后 git commit/push。
- **读 root**：已在 system prompt 里，不用读。
- **读深层**：靠 `Memory` 工具**一层一层展开**：

  > "Read deferred memory from your memory filesystem. Your root memory files are already in your system prompt. Everything else is deferred: the `<deferred-memory>` section lists directories you have not opened. Use this tool to open them progressively instead of guessing what they contain."
  > —— `src/tools/descriptions/Memory.md`，https://raw.githubusercontent.com/letta-ai/letta-code/main/src/tools/descriptions/Memory.md

  它的调用语义：`Memory("projects")` 返回 `projects/MEMORY.md` + 直接子项；`Memory("projects/code")` 再下一层；`Memory("projects/example.md")` 取单文件。**每次最多列 10 条，按最近编辑排序**。

- **有没有 ls/cat/grep/open/commit**：**没有一套专门的记忆专用命令集**。设计取向恰好相反——直接复用 agent 已有的通用工具：`LS` / `Read` / `Grep` / `Glob` / `Edit` / `Write` / `ApplyPatch`，加上 git 本身做 commit。工具清单见 https://github.com/letta-ai/letta-code/tree/main/src/tools/descriptions
  - 官方另有一个可选包 `memfs-search`（`letta install npm:@letta-ai/memfs-search`）提供关键字/语义/混合检索，语义模式依赖外部 `QMD`。
    > "MemFS does not include a semantic or vector index by default. Agents find memory in its Markdown files with normal file-search and read tools."
    > —— https://docs.letta.com/concepts/memfs

### 3.5 硬性约束（这是「可复现细节」里最有价值的一组数字）

MemFS 用 **git pre-commit hook 装了一个校验器**，默认值写在 `DEFAULT_MEMORY_CONSTRAINTS_CONFIG`：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `maxDepth` | `2` | 仓库根到记忆文件之间允许的目录层数 |
| `maxFileCharacters` | `20_000` | 单个投影出的 Markdown 文件字符上限 |
| `maxCoreMemoryCharacters` | `65_536` | 所有 root 文件合计（进入 system prompt 的部分）字符上限 |
| `fileCharacterLimits` | — | 按 glob 的顺序覆盖，第一个匹配生效，`null` = 不限 |
| `readOnlyFiles` | — | 相对 HEAD 保护某些文件的内容/路径/mode |

来源：`src/memory-constraints.ts`，https://raw.githubusercontent.com/letta-ai/letta-code/main/src/memory-constraints.ts
配置文件是可选的 `.memfs.config.json`，注释明确：**「File limits count the complete staged file, including frontmatter」**，且「Commits are blocked only by problems in files they add, change or remove」。

**对比 §2 的软限制：这里是硬阻断（block commit），而且是事前校验。这是 Letta 自己两年间的进化方向。**

### 3.6 sleep-time compute

**论文**：Lin, Snell, Wang, Packer, Wooders, Stoica, Gonzalez, *Sleep-time Compute: Beyond Inference Scaling at Test-time*, arXiv:2504.13171（2025-04-17）
https://arxiv.org/abs/2504.13171
**博客**：https://www.letta.com/blog/sleep-time-compute

定义（博客原文）：

> "Sleep-time compute is a new way to scale AI capabilities: letting models 'think' during downtime. Instead of sitting idle between tasks, AI agents can now use their 'sleep' time to process information and form new connections by **rewriting their memory state**."

**是不是后台 subagent 整理记忆？——是。** 博客有一节标题就是 `MemGPT 2.0: Sleep-time agents in Letta`，并给了「Configuring sleep-time agents」。

Python 版实现（`archive` 分支 `letta/groups/sleeptime_multi_agent_v4.py`）的机制：

- sleep-time agent 是**同组（group）里的另一个 agent**，有独立 system prompt（`letta/prompts/system_prompts/sleeptime_v2.py`，开头是 `You are Letta-Sleeptime-Memory... You run in the background, organizing and maintaining the memories of an agent assistant who chats with the user.`）。
- 触发条件：`sleeptime_agent_frequency` 计数器，`turns_counter % frequency == 0` 才跑；`None` 表示每轮都跑。
- 跑在主 agent `step()` 之后，是 fire-and-forget 的后台任务（`_issue_background_task`）。
- 有 `get_last_processed_message_id_and_update_async` 做增量，只处理新消息。
  来源：https://raw.githubusercontent.com/letta-ai/letta/archive/letta/groups/sleeptime_multi_agent_v4.py

sleeptime prompt 里的关键指令（可抄的「整理记忆的语气」）：

> "Use your precise tools to make narrow edits, as well as broad tools to make larger comprehensive edits. To keep the memory blocks organized and readable, you can use your precise tools to make narrow edits (additions, deletions, and replacements), and you can use your `rethink` tool to reorganize the entire memory block at [once]..."
> —— `sleeptime_v2.py`

### 3.7 dreaming

**dreaming 是 sleep-time 在 2026 的新名字/新形态**，官方文档：

> "**Dreaming** uses **background subagents** to review recent conversations, consolidate useful lessons, and update memory without interrupting your active work. Configure dreaming with `/sleeptime` in the CLI or **Dream settings** in the app. Choose when it runs: **after a set number of completed agent steps or when the context window is compacted**. Select **Agent reviews before applying** to have your agent review and revise proposed memory updates in a second background conversation. This uses more model tokens and does not ask you for approval."
> —— https://docs.letta.com/configuration/memory

注意两个细节：
1. 命令行开关叫 `/sleeptime`，产品名叫 dreaming —— 术语没统一。
2. 触发点之一是 **「context window 被压缩时」**，即 compaction 会顺带触发记忆整理。这是个很聪明的耦合。

内建 subagent 表（官方）：

| Subagent | 用途 | 权限 |
|---|---|---|
| `recall` | 搜历史对话 | 只读 |
| `init` | 从当前项目快速初始化记忆 | 读写 |
| `reflection` | **Background "sleep-time" memory consolidation** | 读写 |

> "`recall` is the only built-in preset the main agent can select with `subagent_type`; custom subagents can be selected the same way. **The harness launches `init` and `reflection` itself.**"
> —— https://docs.letta.com/configuration/subagents

**「harness launches it itself」= 这是 runtime 级能力，不是 agent 自主决定。** 这一条对 §7 的分栏判定很关键。

CLI 侧还有 `letta dream --to`（维护 AGENTS.md）、`letta dream --from`（反思外部来源）、reflection 模型覆盖等，见 changelog：https://docs.letta.com/reference/changelog

## §4 上下文压缩与预算

### 4.1 论文版（2023）：token 阈值 + 预警 + 递归摘要

原文（已逐字核对）：

> "When the prompt tokens exceed the **'warning token count'** of the underlying LLM's context window (e.g. **70%** of the context window), the queue manager inserts a system message into the queue warning the LLM of an impending queue eviction (a **'memory pressure' warning**) to allow the LLM to use MemGPT functions to store important information contained in the FIFO queue to working context or archival storage... When the prompt tokens exceed the **'flush token count'** (e.g. **100%** of the context window), the queue manager flushes the queue... the queue manager evicts a specific count of messages (e.g. **50%** of the context window), generates a **new recursive summary using the existing recursive summary and evicted messages**. Once the queue is flushed, the evicted messages are no longer in-context... however they are stored indefinitely in recall storage and readable via MemGPT function calls."
> —— §2.2，https://arxiv.org/html/2310.08560v2

**这套设计的三段式值得照抄**：预警(70%) → 给模型机会自救 → 到点强制驱逐(100%, 砍 50%) → 递归摘要接续。

`memory pressure` 在代码里是有实体的：
> `MESSAGE_SUMMARY_WARNING_STR = "The conversation history will soon reach its maximum length and be trimmed. Do NOT tell the user about this system alert... you should save that information immediately by calling function core_memory_append, core_memory_replace, or archival_memory_insert."`
> —— `letta/constants.py`

注意它连「别告诉用户」都写进去了——这是 prompt 工程的细节。

### 4.2 Python 版（2024-2025）：改为按消息条数，不是 token

`letta/settings.py`：

```python
class SummarizerSettings:
    mode: SummarizationMode = SummarizationMode.PARTIAL_EVICT_MESSAGE_BUFFER
    message_buffer_limit: int = 60
    message_buffer_min: int = 15
    enable_summarization: bool = True
    max_summarization_retries: int = 3
    partial_evict_summarizer_percentage: float = 0.30
```
来源：https://raw.githubusercontent.com/letta-ai/letta/archive/letta/settings.py

代码注释直言退步了：
> "Summarization as implemented in the original MemGPT loop, **but using message count instead of token count**."
> —— `letta/services/summarizer/summarizer.py`

**这是一个真实的架构退化**：论文用 token 预算，实现按条数。对「长消息/短消息」不敏感。

递归性确认：它把 `message[1]` 替换成递归摘要，即 **summary 会喂给下一轮 summary**（真递归，不是分块重摘）。

### 4.3 2026 版：sliding_window + 10% 递增

官方现行文档：

> "**Mode**: `sliding_window` (keeps recent messages, summarizes older ones); **Model**: Provider-specific default (`claude-haiku-4-5`, `gpt-5-mini`, or `gemini-2.5-flash`), falling back to the agent's model; **Sliding window**: `sliding_window_percentage=0.3` (summarizes ~30% of messages and keeps ~70%; **increases the summarized portion in ~10% steps if needed** to fit the token budget); **Summary limit**: 50,000 characters"
> —— https://docs.letta.com/v1-sdk/messages/compaction

代码印证（`src/backend/local/compaction.ts`）：

```ts
export const LOCAL_DEFAULT_SLIDING_WINDOW_PERCENTAGE = 0.3;
const ALL_WORD_LIMIT = 500;
const SLIDING_WORD_LIMIT = 300;
...
let evictionPercentage = percentage;
while (approxTokenCount >= goalTokens && evictionPercentage < 1.0) {
  evictionPercentage += 0.1;
  ...
}
```
来源：https://raw.githubusercontent.com/letta-ai/letta-code/main/src/backend/local/compaction.ts

**策略判定**：
- **是递归摘要吗？** 是，但换成了「上一份 summary 作为输入继续滚」的滑窗式，不是论文那种「summary + 被驱逐消息合成新 summary」的严格递归。
- **是分块吗？** 不是固定分块，是**按消息条数比例切**，切不够就每次多切 10%，直到 token 数降到 `(1-p)*contextWindow` 以下。
- **有 token 计数吗？** 有，但是**估算**而非 tokenizer：

  > "We intentionally avoid tokenizer dependencies here. The estimate is used only as a safety guard before sending prompts to the API; using **4 chars/token** is conservative enough for English/Markdown prompts while keeping the codepath synchronous and dependency-free."
  > —— `src/agent/subagents/context-budget.ts`

  即 **`estimateTokens = ceil(len/4)`**，粗粒度。

### 4.4 预算控制的具体数字

`context-budget.ts` 里的硬编码：

```ts
export const STARTUP_CONTEXT_ESTIMATED_CHARS_PER_TOKEN = 4;
export const REFLECTION_STARTUP_CONTEXT_TOKEN_LIMIT = 16_000;
export const REFLECTION_PARENT_MEMORY_SNAPSHOT_CHAR_LIMIT = 40_000;
```
来源：https://raw.githubusercontent.com/letta-ai/letta-code/main/src/agent/subagents/context-budget.ts

即 **reflection/dreaming subagent 的启动上下文硬顶 16k tokens（≈64k 字符），其中父 agent 的记忆快照最多 40k 字符**，超了就截断并插一条 `[Reflection startup context truncated...]` 提示。

### 4.5 eviction 策略汇总

| 版本 | 触发 | 驱逐量 | 摘要方式 | 摘要写回哪 |
|---|---|---|---|---|
| 论文 2023 | 70% 预警 / 100% 强驱 | 50% 上下文 | 严格递归摘要 | FIFO queue[0] 作为 system message |
| Python 2024-25 | 消息数 > 60 | 30%（`partial_evict_summarizer_percentage`） | 递归（替换 message[1]） | 上下文内 message |
| TS 2026 | token 估算超 `(1-p)*ctx` | 30% 起，每次 +10% | 滑窗摘要，限 50k 字符 | 上下文内，可配 self-compaction |

另有一条工程细节值得注意（`compaction.ts` 注释）：
> "Pressure compaction is opportunistic: it must not fail a turn (or a completed response)."

即**压缩失败不能拖垮这一轮对话**——这是生产环境必须的处理。

### 5.5 是否需要外部向量库？

**分代回答，这是重点**：

- **archival memory（Python 版）**：是，用 **pgvector**（Postgres 扩展）。`compose.yaml` 里 `ankane/pgvector:v0.5.1`。文档称其为 "a general-purpose vector DB"。来源：https://docs.letta.com/v1-sdk/memory/archival-memory
- **还支持 Turbopuffer** 作为可切换后端：
  ```python
  if archive.vector_db_provider == VectorDBProvider.TPUF:
      # use hybrid search to combine vector and full-text search
  # Fall back to SQL-based search for non-vector queries or NATIVE archives
  ```
  来源：`letta/services/agent_manager.py`；客户端 `letta/helpers/tpuf_client.py` 开头即 `"""Turbopuffer utilities for archival memory storage."""`
- **MemFS（2026）**：**默认不需要向量库**。
  > "MemFS does not include a semantic or vector index by default. Agents find memory in its Markdown files with normal file-search and read tools."
  > —— https://docs.letta.com/concepts/memfs
  语义检索是可选 mod（`@letta-ai/memfs-search` + 外部 `QMD`）。

**结论：2026 的 Letta 已经把「记忆」从「向量库」解耦成「git 仓库 + 文件工具」。这是它最重要的架构转向。**

### 5.6 单次记忆操作要几轮 LLM 调用

**这是「未查到官方明确数字」的一项**，但可以从机制推出下界，并注明依据：

- **一次「写记忆」最少 1 轮**（模型输出 tool call）+ 1 次工具执行，但**要把工具结果返回给模型才能继续对话 → 实际 ≥ 2 次 LLM 调用**（tool call 轮 + tool result 后继续生成轮）。
- 论文的 `request_heartbeat=true` 允许**在同一轮内链式多次推理**，所以「检索 → 再检索 → 回答」可能是 3-5 次调用，取决于模型决定链几次。来源：§2.4。
- **sleep-time / dreaming 额外再烧一个 agent 的完整 turn**（甚至「Agent reviews before applying」开启后是**两个**后台会话）：
  > "Select 'Agent reviews before applying' to have your agent review and revise proposed memory updates in a **second background conversation**. This uses more model tokens and does not ask you for approval."
  > —— https://docs.letta.com/configuration/memory

**明确写「未查到」的部分**：Letta 官方没有公布「一次记忆操作平均 N 次 LLM 调用」的基准数字。任何具体数字（比如"3.2 次"）都是编的。

## §6 公认的坑（具体，带出处）

### 6.1 弱模型根本不会用工具 —— 最著名的一条

Issue #1776 标题就是吐槽：
> "**MemGPT code is AAA+ unfortunately I cannot get it to work (no matter which LLM I try I cannot get it to work reliably)**"
> —— https://github.com/letta-ai/letta/issues/1776

这类问题在 Letta 的架构下是**结构性**的：整个记忆系统依赖模型主动发起 tool call，模型不发就完全没记忆。这不是 bug，是设计代价。

### 6.2 memory block 超限后「数据已写入但校验失败」——数据损坏

PR #1616 的复现（原文）：
> "Make agent core memory (human or persona be 1999 characters with a 2000 limit) Ask agent to save something more to the memory. If it does actually do it, the validation and function call would fail **but the data was still applied to the agent**. On next agent load it will throw an error because the memory is over the limit."

同一 PR 还修了另一个更诡异的 bug：
> "have the AI update a memory block with `core_memory_replace` and have it send `""` for old content. It will replace the text with a **huge blob (size based on # characters on the existing content in that bank)**"
> —— https://github.com/letta-ai/letta/pull/1616

**即：`old_content=""` 会导致内容爆炸式重复。** 这是「精确子串替换」这种记忆 API 的经典陷阱（空串是所有位置匹配），非常值得记下来。

### 6.3 block 冲突覆盖 / 最后写入者赢

官方文档自己承认：
> "**Setting `value` completely replaces the entire block content** - it is not an append operation. If multiple processes (agents or external scripts) modify the same block concurrently, **the last write wins and overwrites all earlier changes**."
> —— https://docs.letta.com/v1-sdk/memory/memory-blocks

多 agent / 多 subagent 场景下这是真问题，也是 Letta 后来上 git 的动机之一（git 能做 conflict detection）。

2026 版为此专门写了 `memory-conflict-repair.ts`，处理 `MERGE_HEAD` / `REBASE_HEAD` / `CHERRY_PICK_HEAD` / `REVERT_HEAD` 状态：
来源：https://raw.githubusercontent.com/letta-ai/letta-code/main/src/agent/memory-conflict-repair.ts
—— 也就是说：**上了 git 之后，冲突问题没有消失，而是从「静默覆盖」变成了「需要修复的 merge conflict」**。

### 6.4 记忆块膨胀 / 记忆隔离

- **跨 agent 记忆隔离**（2026）：
  > "Critical: Memory isolated per-agent; new sessions get blank slate regardless of working memory in other agents... Memory built in one agent is **completely invisible** to all other agents -- including when starting a new session. The local backend creates an isolated memory directory per agent ID, with no mechanism to discover, link, or load another agent's memory."
  > —— https://github.com/letta-ai/letta-code/issues/2666
- **记忆需要定期"体检"**：官方为此提供了 `/doctor`：
  > "If the memory hierarchy has drifted or grown too large, run `/doctor` to **audit placement, duplication, and system-prompt token usage**."
  > —— https://docs.letta.com/configuration/memory
  **官方专门做了一个工具来治「记忆膨胀」，说明这是常态问题。**
- **大仓库克隆超时**（2026）：
  > "Memory checkout clone-swap of large shared-memory repos races a ~3 min deadline and aborts" —— https://github.com/letta-ai/letta-code/issues/5091

### 6.5 成本 / prompt caching 被破坏

**这是最有技术含量的一条吐槽**，来自官方论坛，而且得到了 Letta 方（ezra）的正面回应：

> 用户问："Modifying memory blocks during a live conversation between agent and user (or agent-to-agent) should come at a **latency/$$$ cost, as context inserts and evictions breaks prompt caching**. What are Letta's thoughts on navigating that trade-off?"
>
> ezra 答："**Letta implements prompt caching, and memory block edits only invalidate the cache for that single turn.** The invalidation is temporary and localized - the cache recovers on the next turn where no ed[its]..."
> —— https://forum.letta.com/t/breaking-prompt-caching/149

**关键机制**：memory block 被 prepend 在 system prompt 里 → 改 block = 改 prompt 前缀 = **整个 KV cache 失效**。这是「core memory 常驻上下文」这一设计的**固有代价**，不是实现问题。因此高频改记忆的 agent 成本会显著高于普通 agent。

成本量级（官方定价页）：
> "**Casual coding users** (a few hours per day): Typically **~$100/mo+** usage; **Power users** (long sessions, many parallel agents): Often approach or exceed **$200+/mo**"
> —— https://docs.letta.com/pricing

### 6.6 调试困难

- 记忆状态是「模型自己改的」，出问题时要回溯「哪一轮改了哪个 block」——Python 版为此有 `BlockHistory` / checkpoint / undo-redo（`checkpoint_block_async`，见 `BlockManager`），MemFS 版直接用 git log，**这本身就是承认了可观测性是真痛点**。
- `ContextWindowOverview` 这个 schema（"Overview of the context window, including the number of messages and tokens"）说明**需要专门接口才能看清上下文里到底有什么**。

### 6.7 安全：记忆投毒可跨会话持久化

> "[Bug]: Cross-Session State Leakage via Persistent Core Memory Poisoning (Sandbox Isolation Failure)... agents can utilize internal tools (e.g., `core_memory_replace`) to maliciously alter their persona. Because the server lacks a hard tear-down or atomic block-flushing mechanism between independent tasks on the same daemon, these malicious memory modifications are **permanently written to the database**."
> —— https://github.com/letta-ai/letta/issues/3388

**这条对任何抄这套设计的系统都成立**：记忆是持久的、agent 可写的、又会被注入 system prompt → 它是 prompt injection 的持久化载体。

### 6.8 「未查到」的项

- 没有找到**权威的第三方基准测试**（延迟 ms / 每次记忆操作成本 $）——Letta 官方也没发。
- 没有找到 HN / Reddit 上**可引用的一手高赞讨论串**（搜索结果里的 Reddit 镜像和二手博客无法确证原帖，故不引用）。
- 没有找到官方公布的「sleep-time agent 平均节省多少 token」的量化结论。

## §7 可移植性分栏表（最重要的一节）

**判定标准**：问「这件事是否必须由**掌控完整 agent loop 和完整上下文**的那一方来做？」如果只需要「pre-step 钩子 + 动态 tool 注入 + 能读改 system prompt 片段」，那就是插件可做。

### 7.1 必须自己是 runtime 才能做

| 能力 | 为什么必须是 runtime | 证据 |
|---|---|---|
| **把记忆块拼进 system prompt 的固定位置**（`<memory_blocks>` prepend） | 需要**拥有 prompt 组装权**。插件通常只能 append 或作为 tool result 注入，无法插入到 system prompt 中间 | memory-blocks 文档："simply prepended to the agent's prompt" |
| **FIFO queue 的自动驱逐 + 递归摘要**（70% 预警 / 100% 强驱 / 砍 50%） | 需要**拥有消息历史的所有权和裁剪权**。插件的 pre-step 钩子看得到历史但通常不能删历史 | 论文 §2.2 |
| **memory pressure 预警注入（作为 system message 插进队列）** | 需要能**伪造一条 system 消息进对话流**，多数插件 API 不允许 | `MESSAGE_SUMMARY_WARNING_STR` |
| **每轮 turn 结束后自动触发后台 agent**（`the harness launches init and reflection itself`） | 需要**生命周期所有权**：turn 结束事件 + 起后台任务的权限 | subagents 文档原文 |
| **sleep-time agent 作为同组第二个 agent 并行跑**，并共享/写同一份记忆 | 需要**多 agent 编排 + 共享状态**，插件没有 group 概念 | `sleeptime_multi_agent_v4.py` |
| **compaction 触发时顺带触发 dreaming** | 需要同时掌握 compaction 和 memory 两个子系统 | memory 文档："or when the context window is compacted" |
| **对 block 写入做硬校验（limit/maxDepth/readOnly）并阻断 commit** | 需要**在工具执行链路上有否决权**（装 pre-commit hook 也算，但那要求它拥有磁盘上的仓库） | `memory-constraints.ts` |
| **git checkout 的生命周期管理**（clone / 冲突修复 / 跨机器同步 / 3min 超时） | 需要**拥有执行环境和进程** | `memory-conflict-repair.ts`、issue #5091 |
| **token 预算的全局核算**（`maxCoreMemoryCharacters=65536` 这类跨文件合计） | 需要**在发送请求前看到完整 final prompt** | `context-budget.ts` |
| **让模型"看见" chars_current/chars_limit 并据此自我约束** | 需要**控制 prompt 内容的渲染**，而不只是提供工具 | memory-blocks 文档的 XML 示例 |

### 7.2 任何拿到 pre-step 钩子 + 动态 tool 注入的插件都能做

| 能力 | 为什么插件够了 | 备注 |
|---|---|---|
| **提供 `core_memory_append` / `replace` / `insert` / `rethink` / `apply_patch` 这套工具** | 纯粹是「注册工具 + 实现读写」。读写目标是插件自己的存储 | 这就是 MemGPT 记忆系统的**全部可移植部分**，也是价值最高的部分 |
| **`description` 字段引导模型何时用哪个 block** | 纯 prompt 工程，写在 tool description 里即可 | memory-blocks 文档强调 description 是「main indicator」 |
| **memory block 的数据模型（label/description/value/limit）** | 就是一个 KV + schema | 注意 limit 要做**事前硬校验**，别学 Letta 的软限制 |
| **记忆的按需加载 / progressive disclosure** | 插件可以在 pre-step 里根据当前任务，把自己的记忆文件摘要塞进上下文（或作为额外的 system 片段 append） | 不能插到 system prompt 中间，但 append 到末尾效果接近 |
| **`Memory("path")` 这种逐层展开的读取工具** | 纯工具实现 | 一次最多列 10 条、按 mtime 排序，这些细节可直接抄 |
| **git 版本化记忆仓库本身** | 插件可以自己在磁盘上维护一个 git repo，读写都走文件工具 | 前提：有可写的本地盘。云端插件需自备存储 |
| **按需的语义/关键字检索（memfs-search 等价物）** | 插件可挂自己的向量/全文索引 | 这块和 Letta 无耦合 |
| **记忆整理（sleep-time 的"整理动作"本身）** | 插件可以在 turn 结束后（如果有 post-turn 钩子）或下一个 pre-step 里，起一次独立的 LLM 调用做整理 | **能整理**，但**不能强制**在「compaction 时」或「每 N 个 harness step」精确触发——那需要 runtime |
| **"Agent reviews before applying" 的双重审阅** | 就是调用两次 LLM，插件可做 | 纯成本换质量 |
| **记忆冲突检测（读时比对、报 conflict）** | 插件自己做版本比对即可 | git 的 merge conflict 是通用能力 |
| **token 计数与预算（粗估）** | `len/4` 这种估算插件完全能做 | 精确 tokenizer 也不难 |
| **把「别告诉用户这是系统提醒」写进提示** | 纯 prompt 技巧 | 直接抄 `MESSAGE_SUMMARY_WARNING_STR` 的措辞 |

### 7.3 一句话总结分栏逻辑

**Letta 的记忆系统 = 「可移植的记忆数据层 + 不可移植的上下文所有权」。**

- **可移植的部分（80% 的价值）**：工具 schema、block 数据模型、description 驱动的路由、progressive disclosure 的目录约定、git 版本化、limit 校验、整理用的 prompt。这些**和谁是 runtime 无关**。
- **不可移植的部分（决定"像不像 MemGPT"）**：能不能**改 system prompt 的指定位置**、能不能**删历史消息**、能不能**在 turn 边界起后台 agent**、能不能**在 compaction 时刻挂钩**。这四件事全部依赖「我拥有这个 agent loop」。

**给插件路线的实操建议**：
1. 记忆本体（blocks + git 仓库）做成插件自有状态，**不要**试图塞进宿主 prompt 中间。
2. 常驻记忆用「pre-step 时 append 一段 `<memory>` 到上下文」近似替代「prepend 进 system prompt」——**代价是 prompt cache 前缀更不稳定**，要把记忆段放在**最稳定**的位置（比如紧跟 system prompt 之后，且内容按 label 排序稳定输出）来减轻 §6.5 的问题。
3. 换页（eviction）不要自己删历史（做不到），改成**在 pre-step 里对历史做压缩性重写**（如果宿主支持编辑历史）或**把摘要作为一条新的 user/system 消息插入**。
4. sleep-time 用「post-turn 钩子 + 异步 LLM 调用」实现，接受「不能精确对齐 compaction 时刻」的损失。
