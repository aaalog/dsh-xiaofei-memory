## 根因分析：为什么蒸馏仍然是 0

这不是参数没调好，是**两个结构性原因叠加**。我做了实测验证（用生产库副本模拟，未动生产数据）：

### 原因一：只扫描 `recent` 层，而该层几乎是空的

```js
// src/sleep.js:30
export async function runNightlySleep(db, { summarize, layer = "recent", logger } = {})
//                                                    ^^^^^^^^^^^^^^^^ 默认只扫 recent
```

实测三层分布：

| 层 | 记忆数 | 动态阈值 |
|---|---|---|
| recent | **2** | 3 |
| weekly | 5 | 3 |
| core | 13 | 3 |

**recent 层只有 2 条，而要「同实体 > 3 条」才蒸馏——数学上不可能触发。**

### 原因二：即使扫描全部三层，仍然不会触发

我用生产库副本跑了「扫描全部三层」的模拟，结果：

```
[recent] scanned=2  threshold=3  groups=0  archived=0
[weekly] scanned=5  threshold=3  groups=0  archived=0
[core]   scanned=13 threshold=3  groups=0  archived=0

after: origin_ids non-empty = 0
```

全库实体共现统计（阈值需 > 3）：

| 实体 | 记忆数 | 是否达标 |
|---|---|---|
| `小肥2号` / `2号` / `小肥鱼` / `小肥` | 各 **4** | 差 1 条 |
| 其余全部 | ≤ 2 | 否 |

**最大只有 4 条，需要 > 3（即 ≥4）——刚好卡在边界。**

等等，4 > 3 应该满足。但模拟里 groups=0。原因：这 4 条都记在不同层（core 13 条里），而**单层扫描时 core 层的 `小肥2号` 只有 3 条**（第 4 条在 weekly 层）。跨层不算同组。

### 原因三（附带发现）：实体抽取质量仍然差

仍能看到这些实体入库：

```
'. Current the assistant runtime Web GUI URL:'   ← 整句英文
'<teammate name>'                                ← 模板占位符
'...'                                            ← 省略号
'| p ==='                                        ← 代码残片
```

`isMeaningfulEntity` 只过滤了词典里的常见词，**挡不住这类结构性垃圾**。

## 我建议的修复方案（等你确认，不自行实施）

### 方案 A：阈值改为「跨层 + 相对比例」（推荐）

- 实体分组跨所有层合并（同一实体在 core/weekly 各 3 条，应视为 6 条）
- 阈值改为「该实体的层内密度」，而非绝对条数
- 预计效果：`小肥2号` 等 4 个实体立刻达标

### 方案 B：改为「时间窗口聚合」

不看实体，改看「同一时间段的记忆」。你现在的库很小，按天/周聚合更现实。

### 方案 C：加强实体抽取

- 过滤纯英文长句、模板占位符、代码残片
- 但你只有 20 条记忆，**即使实体变干净，数量仍不足以触发任何有意义的蒸馏**

## 我的判断

**方案 A + B 结合**才有实际意义。单纯调阈值或洗实体，在这个只有 20 条记忆的库上都无法产生有意义的蒸馏结果。

更根本的问题是：**你的记忆库太小（20 条），而这个机制是为「几百上千条」设计的。** 现在讨论蒸馏质量为时过早，可能等到记忆量上去之后问题自然消失。

**建议：这个功能先放一放，等记忆积累到 100+ 条再看。** 现阶段 A 档（常驻记忆）已经在正常工作，那才是真正解决「重要记忆能被看到」的部分。
