## 2. 我要更正的三处

### 2.1 「README 没提启动补偿」→ 代码里有，是我文档漏写

`src/index.js` 第 386-390 行：

```js
// Compensation: run sleep on startup if it's been >24h since the last pass.
const lastSleep = Number(metaGet(db, LAST_SLEEP_KEY) ?? 0);
if (lastSleep === 0 || Date.now() - lastSleep > 24 * 3600 * 1000) {
  queueMicrotask(() => void doSleep());
}
```

**启动时会补跑**。README 没写这条，是我的文档缺陷，我会补上。

### 2.2 「3 天积压会被一次性喂给 LLM」→ 不会，有硬上限

蒸馏按 `(角色, 实体)` 分组，**每组每晚只取最强的 8 条**喂给模型，归档的也正是这 8 条，其余留到下一晚：

```js
const summarised = unique.slice().sort(...).slice(0, 8);   // 喂 8 条
const ids = summarised.map((m) => m.id);                    // 只归档这 8 条
```

所以 3 天积压的后果**不是幻觉，是慢**——几百条要按每晚 8 条/组消化很多天。这个设计是我上一轮专门为修「8 进 20 出」的数据丢失而改的。

**但你的直觉指向了一个真问题**：慢到一定程度，蒸馏就失去意义了。这也是我接受"水位线触发"的原因。

### 2.3 你没看到的事实：**蒸馏现在根本没有产出**

这是我认为最该先讲的一条。

最近一次夜间（11-28 03:00）的真实记录：

```json
{
  "threshold": 10, "scanned": 211,
  "distilledGroups": 0, "distilledMemories": 0, "archived": 0,
  "skippedEntities": 2367, "skippedGroups": 3,
  "distillSkipped": null
}
```

`skippedGroups: 3` 意味着**3 个组够格**（SpdiamPriduct 15 条 / SQL 14 条 / 豆包 12 条），但摘要**全部返回 null**。

根因链：
1. 宿主 `llm` 服务**只有 `stream()`，没有 `complete()`**
2. 旧代码 `if (typeof llm.complete === "function") … return null` → 永远返回 null
3. 也就是说：`useLlmExtraction` 与蒸馏**从未真正运行过**，一直静默走启发式兜底
4. 两天前我改成 `stream()` 组装（新增 `src/llm-call.js`），`distillSkipped` 从 `no-summarizer` 变成了 `null`——**说明调用确实发生了**
5. **但 3 个组仍然全部返回 null，这个还没定位完**

> 结论：**在蒸馏真正产出摘要之前，讨论"水位线"只是把空跑换一个触发点。**

## 3. Embedding：我实测了，"立刻接一个"比想象的难

你说"立刻接一个本地 Embedding，bge-small 或 nomic-embed-text"。我按这个方向试了现成的路子：

| 测试 | 结果 |
|---|---|
| 本机 OpenAI 兼容代理 `127.0.0.1:57892/v1/embeddings` | **HTTP 404** |
| 该代理的 124 个模型里有 embedding 模型吗 | **没有**（无 bge / m3e / gte / text-embedding） |
| 插件当前依赖 | **零第三方运行时依赖**，仅 `node:sqlite` |

所以"接向量"在**这台机器上**是三选一：

| 方案 | 代价 | 风险 |
|---|---|---|
| **A. 远端 embedding API**（sensenova / agnes） | 需确认它们有 `/v1/embeddings` 且 key 有权限；每轮多一次网络往返 | 断网即退化；隐私（记忆正文出网） |
| **B. 本地模型**（bge-small / nomic） | 引入 `onnxruntime` 原生依赖 → **打破零依赖**；树莓派要算内存与启动时间 | 装不上/跑不动就是死路 |
| **C. 混合（我建议）** | 默认零依赖；配置了 `embeddingProvider` 才启用向量召回；不可用自动退回词面 | 代码多一条分支，但永不因向量不可用而废掉插件 |

**我选 C，并且顺序必须是**：定 provider → 改检索（向量与 FTS 的 RRF 融合）→ 迁移存量向量。

**为什么不能"先接上再慢慢调"**：向量一上，`minSim=0.3` 的地板和 `候选 4000` 的上限**都要重调**。两个变量同时动，出问题就分不清是向量的问题还是词面的问题。

## 4. 我建议的 0.4.0 排期（和他的顺序有两处不同）

他的顺序：Embedding → evolution → 水位线 → 砍 UI

我的顺序：

| 步 | 内容 | 为什么排这里 |
|---|---|---|
| **0** | **修好蒸馏返回 null** | 不然第 1/3 步都在空跑 |
| **1** | 删 `evolution.js` 死代码 + **内置纠错启发式**（他的建议 2） | 便宜、立刻让闭环动起来 |
| **2** | `memory_core_forget` / `memory_core_update` | chat-first 的地基，`trace` 数据已有（`origin_ids`） |
| **3** | **水位线触发**（recent > N 或回合空闲） | 配合第 0 步才有意义 |
| **4** | 砍 UI 到 1 个概览页 | 先有 chat 入口，再砍面板 |
| **5** | **Embedding（方案 C）** | 唯一真正的架构改动，单独排期、单独验证 |

**两处不同及理由**：

1. **Embedding 从第 1 位挪到最后**。不是不认它是地基，而是——**地基要换，得先让上面的东西停下来**。现在蒸馏还在返 null，这时候动检索内核，两个变量一起动，出问题无法归因。
2. **砍 UI 放到 chat 工具之后**。顺序反了会出现空窗：面板砍了、工具还没有，中间几天你将无法管理记忆。
