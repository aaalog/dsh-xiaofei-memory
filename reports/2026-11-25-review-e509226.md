## 3. 新发现

### P1-1 平行事实被当成"冲突"，旧事实被退休（数据可用性）

`keyTokensDiffer` 只要求"双方都有 key token 且集合不相等"，于是**不同实体但句式相同**的两条事实被判为"同一事实的新旧版本"，走 `sim>=0.6 && keyDiff` 的**退休**分支：

```
订单 1234 的退款已经到账，客户已确认
订单 5678 的退款已经到账，客户已确认     sim=0.615 → 1234 被 archived
```

随后 `retrieve("订单 1234 退款")` 返回的是 5678 那条；1234 在 7 天后被物理删除，且**没有任何恢复入口**（见 P2-1）。同类实测：20 条"要点0…/要点1…"顺序写入，19 条前序被退休、只剩 1 条 active——一个带编号的系列笔记会被逐条吃掉。

正确语义应是"关键 token 不同 → 是不同的记忆，**并存**"；只有"同一主语、同一谓词、值不同"才是更正。当前实现把两类都当更正，方向反了。

### P1-2 单数字/单字符值差异被合并吞掉（静默保留旧值）

`KEY_TOKEN_RE = /\d{2,}|…` 只认 2 位以上数字。**单个数字的版本号、阈值、端口尾段、1–9 的计数**根本不产生 key token，`keyTokensDiffer=false`，于是走合并分支（要求 `sim>=0.92`）：

```
本次发布的目标版本是 2.3，发布前必须跑完全部用例再合并，这条规则请一直记住
本次发布的目标版本是 3.3，发布前必须跑完全部用例再合并，这条规则请一直记住
→ merged=true，库里仍是 "2.3"
```

合并分支在等长时保留旧文本，新值 3.3 没有落库、没有告警、没有 `superseded_by`。这是"关键 token 决定"这条新规则最容易踩空的一类输入。

### P1-3 蒸馏产物仍进不了常驻块

摘要行写 core 时没有 `pinned:true`，桩实测 `pinned=0`。默认 `coreMemoryPinnedOnly=true`，`selectCoreMemories` 的 `AND (? = 0 OR pinned = 1)` 会把它挡在块外。结果：**一旦开启 `useLlmExtraction`，蒸馏会稳定产出"只有检索/索引能看到、提示词永远看不到"的摘要**，与 PRD 4.3"core 摘要常驻"的意图相反。块里今天只有 digest 一条 203 tok，预算 642 tok 用了三分之一。

### P1-4 意图提取只认"独立成行"的提问

`intentOf` 在 `lines.length === 1` 时退回"最后一句"，但只要整段粘贴里没有 `。！？；`，句子切分就只有一段，返回的仍是整段 600 字。实测：

- `日志…（80 次重复） 请问 Spdiam 价格配置 评审怎么改？`（同一行）→ 4 条命中，全是**别的粘贴日志**，答案不在；
- `…| …| Spdiam 价格配置 评审怎么改？`（同一行）→ `null`。

用户"先粘贴、再在同一行补一句问题"是常见输入法行为（尤其从终端/IDE 复制时行尾不带换行）。建议：当尾部长度 >120 字且含 `？/?` 时，取**最后一个问号**所在的分句（回退到上一个 `，、；`），不要依赖句子切分。

### P1-5 生产库未迁移、运行进程陈旧

`meta.bridge.build=20261125024559`，HEAD dist 是 `20261125025635`；`PRAGMA table_info(memories)` 只有 `id, role_id, layer, content, entities, origin_ids, strength, created_at, last_accessed, status, pinned`，**没有** `superseded_by`、`archived_at`。实库 `archived=0` 说明旧 build 仍在"归档 → 当晚 purge"。

所以本轮的头号特性（可逆退休 + 7 天保留）在你机器上是**未启用状态**；重启后 `addMissingColumns` 才会 `ALTER TABLE` 并给历史归档行补时间戳（当前无历史归档行，代价为零）。这一点必须写进交接，否则会误判"修了但没效果"。

## 4. P2 / P3

### P2-1 "可逆退休"没有产品级入口
数据留了 7 天、`superseded_by` 也记了，但 `resolveMemoryRef` 只查 `status='active'`，`memory_core_read` 对归档行返回 `{ok:false}`，console 与 bridge 都没有 `restore/unretire` op。想撤回只能手写 SQL——等于"可逆"只对会开库的人成立。要么加 `memory_core_restore(id)`（限保留期内、校验角色），要么在 `memory_core_read` 命中归档行时返回 `{archivedAt, supersededBy}` 并提示可恢复。

### P2-2 租约只覆盖定时通道
- `doSleep` 抢租约，但 `core.triggerNightlySleep()` / bridge `sleep` / 控制台按钮都直接走 `runNightlySleep`，**不抢**；两个手动触发、或手动与 03:00 定时撞车，仍会双跑。
- `releaseSleepLease()` 在 `try` 里、且不在 `finally`：`runNightlySleep` 抛错时租约保留 6 小时，当晚不再有 pass。
- `claimLease` 失败即 `return true`（fail-open），DB 短暂不可用时两个进程都会跑——设计上可接受，但意味着"一夜一跑"是 best-effort。
- 手动 pass 不写 `LAST_SLEEP_KEY`，重启补偿（`>24h` 判定）会在手动 pass 之后再来一次。

### P2-3 4000 上限仍是悬崖
10k 库、10k 命中 → 只评分 id 最小的 4000 行，答案按 id 排最后就被丢；实测 144.6ms/次且发生在 `agent/pre-step` 同步路径上。当前实库 273 条、最慢 22ms，不紧急；但注释里"几十毫秒"的结论应该按 150ms 修正，并把"同词命中 >4000 就丢答案"写进已知限制。真要解决是 bigram 倒排或 bm25 预选，不是继续调 cap。

## 5. 你特别关注的五个问题

**5.1 db.js 合并 0.75 的边界是否合理**
阈值本身已经不是主要矛盾：`0.75` 之上还有 `0.92 && !keyDiff` 的合并分支和 `0.6 && keyDiff` 的冲突分支，实际决策由"关键 token 是否不同 + 相似度落在哪一段"共同决定。本轮实测的边界行为：

- 0.615 + 不同订单号 → 退休旧行（**错**，两条都该留）；
- 0.720 + 不同文件名（`Product.php`/`Search.php`）→ 退休旧行（上轮是"两条并存"，这次动作了，但动作方向仍是"删旧的"）；
- 0.917（`0.3`/`0.4`）、0.867（`11 月 25`/`26`）、0.909（端口 3306/3307）→ 退休，符合"更正"语义；
- 1.000 同文 → 合并；
- 0.946、只差单个数字（`2.3`/`3.3`）→ **合并并保留旧值**。

结论：**"相似度多少"不是关键，"关键 token 不同时应并存还是取代"才是**。当前一刀切"取代"，代价是平行事实被吃掉；而唯一漏判的那类（单数字）又反过来吞掉新值。建议把判定做成三态：`token 不同且主语不同 → 并存`、`token 不同且主语相同 → 取代`、`token 相同 → 合并/取更富有`；`KEY_TOKEN_RE` 至少要覆盖单个数字与 `0.x` 小数、`v2`/`P1` 这类短标识。

**5.2 core-memory 的 KV 缓存稳定性**
不会"每天抖动"。`coreMemorySignature = sha1(id + "\0" + content…)`，`renderCoreMemory` 只拼 `- content`（没有 token 计数），排序 `pinned DESC, strength DESC, created_at DESC, id ASC` 是全序 → 同一库状态必得同一段文本，重启也不变。实库今天块内只有 1 条（digest，203 tok），跨进程稳定。

会破缓存的是**写事件**，不是时间：
1. 新写一条 pinned core 事实（`add_fact`）→ 块多一行；
2. 某条 pinned 行被合并 → `strength` 自增 → pinned 组内**重排**，整段文本变；
3. digest 被编辑/重建；
4. 索引层：排序次级键是 `created_at DESC`，**新增一条 core/weekly 记忆会插到最前，把每一行整体下移** → 整段索引前缀失效。捕获走 `recent`，不进索引，所以日常聊天不会触发；但每次 `add_fact`/蒸馏摘要都会触发一次全段失效。

结论：块本身稳；索引的"头部插入"策略会让每次 core/weekly 写入都付一次前缀缓存。若在意缓存命中率，索引应按稳定键（`id` 或 `created_at ASC`）排序，把新行追加在尾部。

**5.3 sleep 的 `clamp(ceil(size*0.15),3,10)` 随库增长是否合理**
`size` 是**整个 recent 层**行数，阈值只作用到"单个实体组"。实库 273 active → 阈值 10；比例项只在 20–67 行区间有效，低于 20 恒 3、高于 67 恒 10。也就是说：

- 这条"比例阈值"在真实规模下**已经退化成固定 10**，`0.15` 只剩文档意义；
- 单组超过 10 条时，每晚只处理 8 条（summarizer 上限），余量留到下一夜。如果某实体每天新增 >8 条，组永远收敛不了，会稳定保持"每晚蒸馏 8 条"的吞吐；
- 更值得担心的是成本：每晚的 LLM 调用数 = **≥10 条的实体组数**，与库大小成正比、没有全局预算。10k 库若有几百个高频实体，就是几百次 summarize 调用（当前 `useLlmExtraction=false` 所以没暴露）。

结论：阈值本身"够用但不自洽"；真正需要加的是**每夜组数上限 / 总 token 预算**，以及"组内剩余 <3 条就停"的收敛条件。把阈值改成按**组内条数**（如 ≥8 才蒸）比按层大小更贴近直觉。

**5.4 多角色命名空间隔离的泄漏路径**
已修好的：读路径 `roleIdsForAgent` = own + global，`resolveMemoryRef` 带角色过滤（global 读 companion 短 id → denied，单测 7i 覆盖）；写路径 `add_fact` 纠正越权、disabled 命名空间拒写（桩实测 `{ok:false}`）；bridge `search roleId:"global"` 读不到 companion。

仍存在的路径：
1. **捕获兜底落 global**：`roleOf: (sid) => sessionRole.get(sid) ?? config.roleId`，而 `config.roleId` 默认 `"global"`。会话头里没有 `roleId` 时，捕获内容进 global——所有角色都能读。这是最主要的隐性泄漏面（不是"越权读"，是"该私有却写了共享"）。
2. **无 agent 上下文的兼容分支**：`own === undefined` 时 `requested` 任意**已启用**角色都被接受（含 companion/work 互写）。disabled 已挡住，但"启用"不等于"该写"。是否算漏洞取决于宿主 `execute(args, exec)` 是否真的会不带 `agent`——这条从上轮悬到现在，仍未确认。
3. **bridge 的 `all` 作用域**：`roleId:"all"` → `allRoleIds(db)` 全角色可读，而鉴权是 `admit()={}` 即放行 + 页面全局 token。
4. **global 本身是共享命名空间**：任何写进 global 的私人内容，按设计对所有角色可见——这不是 bug，但捕获兜底（第 1 条）会持续把私人内容送进去。

**5.5 并发：`queueMicrotask` 旁轨写 + 主轨读，是否需要显式事务**
不需要"一个大事务"，而且不该有：整个 pass 包在一个事务里会把写锁持有到 LLM 调用结束（当前 summarize 的 `await` 已经在组事务**之外**，这一点是对的）。

现状盘点：`addMemory` 已整体 `withTransaction`（`addMemoryImpl` 在其内）；蒸馏每组一个事务（摘要 + 归档同事务）；`claimLease`/`releaseLease`、`recordSleepRun`、`bumpRecallStats` 的 meta RMW 都已进事务。同一连接内同步 SQLite 不会与旁轨交错；跨进程靠 `busy_timeout=5000` 等锁。

剩下的真实缺口不是"缺事务"，而是：
1. 租约只在一个通道（P2-2）；
2. `withTransaction(async fn)` 会**提前 COMMIT**（上轮实测：await 后抛错行仍在）——当前没有 async 回调，属潜伏陷阱，建议在 `withTransaction` 里显式拒绝 Promise 返回值；
3. 同步等锁最坏 5.5s 冻结主线程（`busy_timeout`），夜间 pass 与用户输入撞车时可见卡顿；把 sleep 的写入批量化/放 worker 才是根治；
4. `LAST_SLEEP_KEY` 与 `RECALL_STATS_KEY` 的重置是事务外两次写（P3-2）。
