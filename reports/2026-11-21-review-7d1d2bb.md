## 1. 上轮 P0 的验证（含残留）

**残留**：分组只做了角色隔离，粒度问题没解决（见 §3.4）。

### 1.2 原子写入与锁：修好了，但换来一次"最长 5.5 秒冻结"

- 嵌套回滚：外层 `withTransaction` 抛错 → 内外两层写入都消失（实测剩余 0 行）。
- 手动 `BEGIN` 内调用 `addMemory`：`db.isTransaction === true` 触发 savepoint 分支，内层失败只回滚内层，外层照常提交（实测外层 1 行、内层 0 行）。`node:sqlite` 确实有 `isTransaction`（我用 `db.exec('BEGIN')` 现场验过 `false → true → false`），这个假设成立。
- 跨进程锁：子进程持 `BEGIN IMMEDIATE` 800ms，父进程 `addMemory` **等待 766ms 后成功**；持锁 6000ms 时等 5536ms 后报 `database is locked`。

**残留（新问题）**：`busy_timeout` 是同步等待，等待期间整个 agent 事件循环停摆。实测 766ms 内主线程完全卡住；最坏 5.5s。`VACUUM`、另一个窗口的长事务、或者用户自己跑脚本，都会让对话"假死"一下。建议：写路径改成"短事务 + 失败入队重试"（后台 flush），或把 timeout 降到 1s 并在失败时降级为内存队列，绝不要让一次 capture 阻塞主线程 5 秒。

### 1.3 存储上限与凭据清洗：主体到位，三处漏口

`util.js:33` `MAX_MEMORY_CHARS = 400`，`db.js:224-229` 先 `scrubSecrets(normalizeContent(...))` 再截断；`addMemory` 外面套了 `withTransaction`，`purgeArchived` 也进了事务（`db.js:518`）。

## 2. 本轮最重要的发现：常驻块已经不是"身份"，是"最近的聊天"

这是我在真实库上跑出来的，不是推测（`selectCoreMemories` 只读调用，参数用默认：650 tokens / 300 字 / strength≥1.0 / 12 条）：

```
core 行数：17
实际进常驻块：7 条，637 tokens / 642 预算（基本饱和）
5 条 core 种子里进去了 2 条：mem_001、mem_003
被挤出去的种子：mem_002、mem_004、mem_005
进块的非种子示例："这次对了，把多余的返回清掉吧，begins仍然保留并…"（strength 1.0，最新）
```

根因是三个默认值叠在一起：

1. 捕获的默认 `strength = 1.0`（`db.js` 捕获路径），而常驻门槛 `coreMemoryMinStrength = 1.0` → **一句闲聊和一条"我是谁"门槛完全相同**；
2. 排序是 `strength DESC, created_at DESC, id ASC`（`core-memory.js:56`）→ 同强度时**越新越靠前**，聊天天然赢过三周前的种子；
3. 预算 650 tokens 只够 7 条（每条 300 字上限，中文按 1 字 1 token），**配额被强度排序吃掉，没有给身份留位置**。

后果不是"少显示几条"，而是：

- 系统提示词里常驻的"我是谁/我怎么做事"被稀释成 2/5，模型的身份感靠记忆检索兜底，而检索又受 §3.2 影响；
- 一条 300 字的对话残片每轮都在付费（637 tokens/轮），**且内容是"这次对了，把多余的返回清掉吧"这种不可迁移的对话上下文**；
- 每次捕获/合并/蒸馏都会改变排序，常驻块文本随之变化 → 10150 之后的前缀失效（KV 抖动），这是上一轮我提的"每天抖动"在生产里的真实版本。

**建议（这条优先级高于一切代码洁癖）**：

- 给 core 加 `pinned`/`soul` 标志：种子和显式"记住"的记忆**先占配额**（例如预算的 40%），剩余才给强度排序；
- 捕获默认强度降到 0.8，常驻门槛提到 1.2，并要求"至少被检索命中 3 次"才晋级；
- 对话残片（含"这次/刚才/继续/对/好的"等指代词且无实体）直接判 recent，不进 core。

## 3. 本轮新发现（按优先级）

### 3.1 长消息召回为 0（P0，实测）

`tokenizeQuery`（`db.js:537-550`）对每个 CJK 片段先加"整段"，再加它的双字组，最后 `slice(0, 24)`——**按出现顺序截断**。一条 1600 字的消息（代码/日志 + 末尾一句真需求）里，前 24 个词项全来自开头那段噪声，末尾的"接口核验"根本没进 LIKE 子句；`buildFtsQuery` 又把整个长片段当作一个 phrase，永不命中。

实测：`"以下是贴过来的一大段代码和日志 "×60 + " 记录12 模块 部署 接口核验"` → **`null`（0 条）**。而这条库里确实有"记录12 模块 部署"的记忆。

这在编码场景里是最常见的输入形态（粘报错、粘 diff、粘日志）。建议：查询只取最后一条用户文本的**最后 2–3 段/最后 400 字**，剥离 ``` 代码块与日志行；每个片段最多取 6 个双字组，全局按"非停用词 + 频次"排序后再凑 24 个；补一个 1600 字回归用例。

### 3.2 候选按强度预截 800 条，会把"最相关但最弱"的那条扔掉（P1，实测）

`db.js:409-412`：先 `ORDER BY strength DESC LIMIT 800`，再算相关性。构造 900 条强度 3.0、只共享"报表/流程"的噪声行 + 1 条 strength 0.3、与查询几乎逐字匹配的记忆：

```
weak-but-relevant row recalled? false (cands cap 800)
```

热门主题（"接口""报表""配置"）在 10k 库里很容易凑满 800 条命中，此时排序权在强度而不是相关性，最该被召回的那条进不了候选。建议：**先按词面命中取全量（或 FTS rank 前 N），再按 score 排序**，强度只参与打分、不参与截断。

### 3.3 10k 规模：54ms/轮，超过 50ms 验收线；FTS 触发器 4 倍写放大

合成 10k 行（角色/层级/时间都真实分布）实测：

| 指标 | 数值 |
|---|---|
| `retrieveForPrompt` 平均（含 LIKE + 打分） | **53.63 ms** |
| 2 字中文查询 | 42.22 ms |
| `addMemory`（含 20 候选 + 事务提交） | 1.86 ms |
| FTS `"部署"`（2 字） | **0 命中** |
| FTS `"部署说明"`（3 字） | 10000 命中 |
| `touchAccessed` 400 次（带 UPDATE 触发器） | 77.2 ms |
| 同上，`DROP TRIGGER` 后 | 19.2 ms → **4.03×** |

两条结论：

- 召回成本是 `O(行数 × 24 个 LIKE)` 的全表扫；227 条时 0.7–4.5ms 很漂亮，10k 就贴着 50ms 线，20k 必超。要么建 bigram 倒排表，要么换 unigram FTS；
- `AFTER UPDATE ON memories` 没有 `OF` 子句（`db.js:55` 附近），`touchAccessed`/`adjustStrength` 每次都在删+重建 FTS 行 → 每轮 8 条召回 ≈ 16 次 FTS 写。改触发器或把访问计数搬到独立表，收益立竿见影。

### 3.4 蒸馏：角色隔离修好了，但"按实体压 12 条 SQL 记忆"仍然会发生

真实库若今晚开启 summarizer（166 条 recent，阈值 10）：

```
可蒸馏组：global/SpdiamPriduct=13、global/SQL=12
```

也就是说：

- "SpdiamPriduct"这个项目词会把 13 条不同侧面的记忆压成 **1 条 300 字摘要**，然后 13 条原文当晚 purge；
- "SQL"这种主题词也会压 12 条互不相关的 SQL 记忆；
- 阈值曲线仍是 `3(≤20) → 6(40) → 10(≥67)`，在小库"4 条就压"，在大库"11 条就压"，与组规模无关。

角色隔离只解决了"串到别人家"，没解决"压得太狠、压错了对象"。建议：阈值改成组内条数 + 强度总和 + 时间跨度（例如"≥6 条且跨 3 天"），摘要前先按子主题聚类，group 容量 41 但只喂 8 条这件事要改（41→8 的压缩率 5:1，信息必然丢）。

### 3.5 事务/并发：三个新的小回归

1. **`withTransaction` 对 async 回调是"提前提交"**。实测：`withTransaction(db, async () => { await …; insert; throw })` → 返回 rejected，但**行已经提交**（可见 1 行）。目前所有调用方都是同步的，但它是 `export` 出来的公共函数，应在开头加 `if (fn.constructor.name === "AsyncFunction") throw`，或断言返回值非 thenable。
2. **统计在提交前累加**。`sleep.js:133` 的 `stats.archived++` 和 `archivedIds.add` 在事务体内执行；一旦回滚，统计和去重集合已经脏了（当前外层抛错会让整个 sleep 抛出，影响有限，但语义不对）。把计数放到 `withTransaction` 返回之后再累加。
3. **锁等待即主线程冻结**（见 §1.2）。
